# DELTA-X v2 — DX02: Method Pre-Registration

**Capability under test** — whether the agent can design an analysis that could *fail*:
declaring, in advance, the threshold each tool must clear to be trusted, the null each
statistic must beat, and the result that would make it abandon the tool.

## 1. Objective

Turn the hypotheses registered in DX01 into an executable analysis plan in which every
proposed measurement carries a pre-declared adequacy check and a pre-declared abandon
condition.

## 2. Inputs

**Given**
- Your own DX01 registration.
- The inventory of what DX03/DX04 will supply: two subfamily FASTA sets of stated size,
  seven reference sequences, and the tool list (MAFFT, HMMER, a coevolution package, a
  structure predictor, a structural aligner).
- The sequence counts you will actually receive, stated up front: **322** sequences in one
  subfamily, **165** in the other, species-unique, 451–616 aa.
- `refs.fasta` carries two references belonging to the smaller subfamily; appending them to
  that subfamily's set before analysis is a legitimate analysis choice.
- `ENVIRONMENT.md` — the absolute path and version of every tool named above.

**Withheld**
- The sequences themselves. No tool may be executed in this stage.

## 3. Required outputs

1. `method_plan.json` — one record per proposed analysis step, each containing:
   - `question` — which DX01 hypothesis this step discriminates, by its identifier.
   - `tool` and `exact_invocation` — the command you intend to run, with flags.
   - `statistic` — what number the step produces.
   - `null` — what you will compare that number against. A null that is a reshuffle of the
     same two groups is **not** sufficient; state a null that could plausibly produce your
     effect by chance. **Gated:** at least one step's null must be a within-subfamily
     split-half null — see Gate A in section 4, which scores the whole task 0 if it fails.
   - `adequacy_check` — a check on whether the **input** can support the method at all,
     with a **numeric threshold stated in advance** and a published or derived source for
     that threshold.
   - `abandon_condition` — the result that makes you drop this step and report a negative.
   - `expected_result_if_H_true` and `expected_result_if_H_false`.

2. `granularity_declaration.json`
   - For each step: the finest spatial granularity at which its output may be reported —
     residue, region, domain, or none — **and the measurement that will establish it**.
   - You may not declare residue granularity without naming the test that would demonstrate
     one position is separable from the position next to it.

3. `power_budget.json`
   - For every sequence-statistical step, the effective sample size you expect, how you will
     measure it, and what you will do if it comes in below your threshold.

## 4. Evaluation — 10 points

Two gates, each worth no points of its own and scored PASS/FAIL, and one scaled item.

| Points | Item |
|---|---|
| 0 (gate) | **Gate A — nulls.** Every differential statistic carries a null that is not a label reshuffle, and at least one is a **within-subfamily split-half** null — comparing two halves of the *same* subfamily to calibrate how much two groups differ for no functional reason. A plan containing no differential statistic fails this gate. FAIL on this gate scores the whole task 0. |
| 0 (gate) | **Gate B — abandon conditions.** Every tool-bearing step carries an abandon condition that some possible result could trigger. A condition that no possible result triggers fails the gate. A plan containing no tool-bearing step fails this gate. FAIL on this gate scores the whole task 0. |
| 10 | **Per-tool adequacy check.** Every proposed tool carries a check on whether the **input** can support the method, with a numeric threshold **declared before execution** and a source. Scored under the four rules below. |

Rules for the 10-point item:

1. **Denominator and rounding.** The unit is one **named executable program** — the binary
   named in that step's `exact_invocation`, counted once however many times it is invoked.
   The award is `10 * (qualifying programs / programs counted)`, **rounded down to the
   nearest 0.5**. *Programs counted* is the larger of (i) the number of named executable
   programs the plan proposes and (ii) **three** — so a plan that proposes a single program
   does not thereby earn full marks. A proposed program carrying no adequacy check counts in
   the denominator and qualifies for nothing. A plan that names no executable program scores
   **0** on this item.
2. **Input-side only.** A plan step whose adequacy check cannot be computed before the main
   analysis is not an adequacy check. A check whose quantity is an output of the step it
   gates scores 0 for that program. Examples that score 0: gating a structure predictor on
   its own pLDDT or PAE; gating a search on its own E-value; gating an aligner on a
   column-reliability score that requires running the aligner.
3. **Sources must be quotable.** A threshold needs a number plus a locator a grader can
   check. A plausible attribution to a document that does not state the number scores 0 for
   that program.
4. **Outcome coupling.** The grader holds a frozen, measured list of which proposed methods
   do and do not work on this input. A declared threshold that would abandon a method on the
   working side of that list forfeits that program's credit, however well sourced.

**Not scored:** the length, breadth or literature coverage of the plan, its step count, or
whether it names the right tools. Plan breadth is a saturated capability — closed-book
models with no tools produce fifteen-to-twenty-step plans naming the same methods. Only the
adequacy thresholds carry points; the nulls and the abandon conditions are gates.

## 5. Scientific constraints

- Adequacy checks are input-side and must be computable before the main analysis — see
  rule 2 in section 4.
- Proposing a method, executing it, and reporting the measurement that shows it inadequate on
  this input is a **success**, not a failure, and is scored as such in DX03/DX04. This is not
  what rule 4 penalises. Rule 4 reaches only a threshold declared *in advance* that is set so
  high it discards a method before any data is seen: a floor you will measure against and
  report is safe, a floor that automatically terminates a method is not.
- Do not propose a method whose output you have already declared you cannot interpret.
- Thresholds must be sourced: "sufficient depth" is not a threshold; a number with a citation
  or a derivation is.

## 6. Success condition

A plan under which an honest execution could return "this does not work, here is the number
that says so" for any step — and under which that outcome would still be scored. Every
pre-declared floor is a quantity to measure against and report, not an automatic stop.
